# ML-сопоставление и КП «по актуальности»

ТЗ п.5.3 прямо оставляет выбор алгоритма нечёткого поиска разработчику
(Levenshtein / TF-IDF / векторный поиск). Здесь зафиксировано, **какой** алгоритм
сделан, **на каких признаках** и **как из него собирается КП**.

Код живёт в двух местах (strangler fig, копии):

- живой путь SPA через шлюз — `src/ProcurementSystem.Services.Matching/`
  (TF-IDF + логрегрессия, кэш модели; каталог по HTTP у Catalog, спецификации — HTTP у Quoting);
- копии в монолите (`src/ProcurementSystem.Infrastructure/Matching/`) и в Quoting
  (генератор КП, стратегия `QuoteStrategy.MlRelevance`).

Точка входа домена — `IRelevanceMatcher`. HTTP живого пути:
`GET/POST /api/matching/{specId}` и те же методы на `/api/specifications/{specId}/match`
(контракт фронта `frontend/src/api/matching.ts` не менялся).

## Задача, которую решает модель

1. По строке заявки (артикул + наименование) найти **актуальный** товар в каталоге:
   точное совпадение, похожее имя, или аналог той же категории.
2. Среди офферов этого товара выбрать поставщика не «просто самого дешёвого», а
   **свежего, с остатком и разумной ценой**.
3. Собрать из этого четвёртый вариант КП, рядом с мин. ценой / мин. сроком / балансом.

Без размеченной выборки «РП кликнул вот этот товар» модель обучается **самостоятельно
на каталоге** (синтетические пары). Это честный unsupervised/self-supervised сетап,
а не «нейросеть с ImageNet».

## Конвейер

```
позиция спецификации
        │
        ├─ 1. точный артикул                     → Kind=ExactSku, P≈0.99
        ├─ 2. кандидаты: TF-IDF posting + Meilisearch top-12
        │     + соседи по категории лучшего хита (аналоги, ТЗ п.5.3)
        ├─ 3. признаки x ∈ R^6
        ├─ 4. логистическая регрессия  P = σ(w·x + b)
        └─ 5. порог: импорт P≥0.5; подстановка в КП P≥0.40
                 │
                 ▼
        товар выбран
                 │
                 └─ ранжирование офферов (линейный score)
                    свежесть цены · остаток · цена со скидкой · срок
                    → строка КП, SelectionReason с разложением
```

## Признаки сопоставления (`x`)

Все в `[0, 1]`. Вектор длины 6:

| i | Признак | Как считается |
|---|---|---|
| 0 | `skuExact` | 1, если артикул заявки = артикул товара (без регистра) |
| 1 | `skuFuzzy` | `1 − Levenshtein(sku)/maxLen` |
| 2 | `nameCosine` | косинус TF-IDF векторов наименований |
| 3 | `tokenJaccard` | Jaccard словесных токенов (без 3-грамм) |
| 4 | `sameCategory` | 1, если токены запроса встречаются в пути категории **и** имя уже хоть чуть похоже |
| 5 | `sameManufacturer` | 1, если имя производителя входит в текст заявки |

TF-IDF: словесные токены (≥2 символа, минус стоп-слова) **плюс** символьные 3-граммы
сжатой строки — так модель переживает опечатки вроде «catalystt» / перестановку букв.

## Логистическая регрессия

\[
P(y=1\mid x)=\sigma(b + w^\top x),\quad \sigma(z)=(1+e^{-z})^{-1}
\]

Стартовый prior (до обучения на каталоге):

```
w = [3.2, 1.8, 2.6, 1.4, 0.9, 0.5],  b = −2.2
```

Точный артикул и косинус имени весят больше категории — как требует ТЗ
(«точное совпадение по артикулу — приоритет»).

Дообучение: SGD, 25 эпох, L2=`0.002`. На каждый товар каталога (до 500):

- плюс: сам товар и он же с перестановкой двух букв в имени;
- минус: случайный другой товар.

Кэш модели (`MatchingModelCache`) живёт в процессе и пересобирается, когда меняется
число позиций каталога.

## Ранжирование офферов (КП «ML»)

Не классификатор, а **линейный score** — его можно прочитать в «причине выбора»:

```
score = 0.28·P(match) + 0.22·fresh + 0.18·stock + 0.20·priceAdv + 0.12·leadAdv
```

- `fresh = exp(−ln2 · ageDays / 45)` — полураспад актуальности прайса 45 дней
  (берётся последняя точка `PriceHistory`, иначе дата оффера);
- `stock` — покрытие заявленного количества остатком, обрезка в `[0,1]`;
- `priceAdv` / `leadAdv` — нормализация среди кандидатов на **эту** позицию
  (как в балансной стратегии, но входят в общий score вместе со свежестью).

Поэтому дешёвый оффер с прайсом двухлетней давности и нулевым остатком проигрывает
чуть более дорогому, но свежему и в наличии.

## Где вызывается

| Место | Порог | Что делает |
|---|---|---|
| Импорт спецификации | P ≥ 0.5 | сразу пишет `ProductId` |
| `GET /api/matching/{id}` (алиас `GET /api/specifications/{id}/match`) | — | превью гипотез, без записи |
| `POST /api/matching/{id}/apply` (алиас `POST .../match/apply`) | P ≥ 0.5 (query `minP`) | проставляет лучшие |
| `POST /api/matching/{id}/apply-one` (алиас `POST .../match/apply-one`) | — | ручной выбор из подсказок |
| `POST /api/matching/suggest` | — | скоринг одной строки `{ sku, name, take }` без спецификации |
| Генератор КП, все стратегии | P ≥ 0.40 | подставляет аналог **в расчёт КП**, спецификацию не меняет |
| Стратегия `MlRelevance` | — | оффер выбирает `OfferRanker`, не min-price |

Экраны: `/specifications/:id/match` (вероятности и кнопки «взять»),
сравнение КП — четвёртая карточка «По актуальности».

## Стенд на 100+ прайсов

Публичные Excel сотни дистрибьюторов пачкой не скачать: прайсы за логином, антибот,
разная вёрстка колонок, лицензии. Для проверки алгоритма в системе собирается
**пересекающийся корпус**, а не парсер интернета.

| Что | Сколько | Зачем ML |
|---|---|---|
| Поставщики `ПЛ-001`… | 120 (20…160) | много офферов на один SKU, разные цена/срок/остаток |
| Номенклатура | **4000 SKU** (ядро Cisco/HPE/Dell/IEK/EKF + `STND-*` дистракторы) | иголка в стоге: синоним должен найти C9300 среди сотен похожих коммутаторов |
| Офферы | ~30–50 тыс. | ядро (~80 SKU) есть у всех 120, хвост — у части |
| Файлы `.xlsx` в архиве | по одному на поставщика, выборка 100 строк | полный прайс в `PriceListItem`; файл — образец импорта |
| Заявка «ML-стенд: кривая заявка» | ~180 строк | точные артикула, опечатки, синонимы «свитч/циско», без SKU, `NO-SUCH-SKU` |

Как залить:

1. Войти как `manager` / `admin`.
2. `/prices` → «Стенд 120×4 тыс. SKU» (первый прогон 1–2 минуты).
3. Открыть ML-сопоставление: в шапке каталог, объём обучения, время прогона, разбивка артикул / ML / аналог.
4. Сравнить 4 стратегии КП, в том числе «По актуальности».

Повторный вызов идемпотентен: поставщики и заявка не плодятся. С CLI, без JWT:
`dotnet run --project src/ProcurementSystem.Api -- seed-corpus`.

Обучение логрегрессии — стратифицированная выборка до 2000 позиций по категориям
(не «первые 500 Cisco»). TF-IDF строится по **всему** каталогу.

Отдельно лежит живой прайс EKF (`docs/ekf_pricelist_2026-03-30.xlsx`, ~20 тыс. строк) —
его грузят через обычный импорт, это не корпус.

## Чего это не делает (честно)

- Нет нейронных эмбеддингов и GPU. На курсовой объём каталога (тысячи–десятки тысяч)
  TF-IDF отрабатывает в процессе API без внешнего сервиса.
- Нет обучения с кликов РП: нет лога «человек подтвердил вот эту гипотезу».
  Когда такой лог появится, те же 6 признаков кормятся в ту же логрегрессию —
  меняется только источник `y`.
- Синонимы как отдельный словарь (открытый вопрос ТЗ №7) не заведены; их роль
  частично закрывают 3-граммы и аналоги категории.
