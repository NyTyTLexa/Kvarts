# Сверка с ТЗ: что реализовано

Источник требований — `docs/ТЗ_plain.txt` (черновик 1.0 от 24.04.2026).
Состояние кода — рабочая копия репозитория на дату сверки.

Документ отвечает на вопрос «что готово относительно функционала ТЗ» и служит черновиком
главы пояснительной записки про реализацию требований. Как система устроена внутри —
в [ARCHITECTURE.md](ARCHITECTURE.md); поля БД — в [DATA_MODEL.md](DATA_MODEL.md);
эндпоинты — в [API.md](API.md).

Статусы в таблицах:

| Статус | Значение |
|---|---|
| **Готово** | Есть backend + живой экран, поведение совпадает с формулировкой ТЗ (допускаются осознанные упрощения модели) |
| **Частично** | Основной сценарий работает, но часть полей/шагов/каналов из ТЗ отсутствует |
| **Мок** | Контракт есть, внешняя система не подключена (или экран декоративный) |
| **Нет** | В коде нет |

## 1. Короткий итог

**MVP из раздела 14 ТЗ закрыт полностью.** Сквозной процесс, ради которого писалось ТЗ,
в системе есть и проходит от Excel до отметки в учётной системе:

```
прайс Excel → каталог → спецификация проекта → 3 варианта КП
    → согласование КБ (наценка/маржа) → счёт NOC → заказ с резервом
    → приёмка склада → выгрузка в WMS/1С (шлюзы)
```

То, чего нет — это в основном «взрослая» обвязка корпоративного контура: настоящие 1С и WMS,
справочник контрагентов, версионирование КП как сущности, KPI с целевыми цифрами,
многошаговый круг согласователей NOC (стадия «Согласован» одна, её ставит КБ).

Грубая оценка покрытия (для защиты, не для бухгалтерии):

| Срез ТЗ | Покрытие | Комментарий |
|---|---|---|
| MVP, обязательные функции (§14) | **11 / 11** | Всё обязательное есть |
| MVP, желательные | **4 / 4** | Fuzzy, аналоги, журнал — есть; прямые API NOC/1С заменены внутренним модулем и шлюзами |
| Use Cases UC-01…UC-10 | **7 готово, 3 частично** | Частично: UC-07 (нет отдельного круга согласователей NOC — одна стадия «Согласован», её ставит КБ; счёт создаётся сам), UC-08 (проверка договора), UC-10 (фильтры/выгрузка отчёта) |
| Функциональные требования §5 | **ядро готово, каталожные поля урезаны** | Импорт, поиск, скидки, 3 стратегии КП, override, согласование — да; десятки опциональных колонок прайса не хранятся |
| NOC §6 | **внутренний модуль, не внешняя система** | Счёт с позициями, статусами и вложениями есть; реквизиты контрагента, НМЦ, отдельный круг согласователей — нет |
| Роли §3 | **6 ролей из 7** | РП, КБ, бухгалтерия, склад, админ, viewer. Отдельной роли «Аналитик» нет — её права = `viewer`/`admin` |
| Интеграции §12 | **2 готово, 2 мок, 1 частично** | Excel — да; email — SMTP/MailHog (на хосте выключено); NOC — внутри системы; 1С/WMS — мок (+ опциональный адаптер ERPNext); AD/LDAP — через Keycloak, не напрямую |

Для курсовой этого достаточно: защищается работающий процесс, а не промышленный контур заказчика.
Ниже — по пунктам ТЗ, без прикрас.

## 2. Сценарии использования

| ID | Сценарий ТЗ | Статус | Где в системе | Чем отличается от ТЗ |
|---|---|---|---|---|
| UC-01 | Загрузка прайса поставщика | **Готово** | `/prices`, `POST /api/pricelist/import` | Гибкий маппинг колонок вместо жёсткой структуры. Архив оригинала, дубли SKU, `.xlsx`/`.xls`. Для объёма ML — `POST /api/pricelist/seed-corpus` (120 прайсов × 4 тыс. SKU, не парсинг сайтов) |
| UC-02 | Загрузка перечня проекта | **Готово** | `/specifications`, импорт Excel, `/quote` | Сопоставление: точный артикул, затем fuzzy Meilisearch. 3 варианта КП считаются на лету |
| UC-03 | Ввод скидок по вендору | **Готово** | `/discounts`, `/api/discounts` | Есть срок с/по (nullable = бессрочно). Цель — поставщик **или** производитель |
| UC-04 | Выбор варианта КП + резерв | **Готово** | `/specifications/:id/quote`, `POST /api/orders/from-quote` | Резерв остатка (`StockQuantity`) при оформлении заказа, возврат при отмене |
| UC-05 | Передача в коммерческий блок | **Готово** | `/approval` (в меню: «Маржа»), `POST /api/approvals`, `…/margin` | Сводка — карточка согласования с себестоимостью/наценкой/маржой. Уведомление — in-app и email (SMTP/MailHog). Подписи экранов — [UI.md](UI.md) |
| UC-06 | Согласование КП | **Готово** | `POST /api/approvals/{id}/decision` (роль `commercial`) | Утвердить/отклонить с комментарием. Resubmit из «Отклонено» |
| UC-07 | Создание записи в NOC | **Частично** | автосоздание при `POST /api/approvals/{id}/decision` (`CreatedBy` = «Система (авто)»); ручной `POST /api/invoices` идемпотентен | Счёт создаётся сам в момент согласования. Круг согласователей NOC не выделен — одна стадия «Согласован», её ставит КБ (10.11). Согласование и создание счёта — два сохранения |
| UC-08 | Фиксация оплаты | **Частично** | `/invoice`, статус + вложения (роль `accounting`); «Согласован» — КБ | Оплата и документы есть. Отдельного шага «проверка договора с поставщиком» нет. Бухгалтерия не может поставить «Согласован» (403) |
| UC-09 | Приёмка на складе | **Готово** | `/warehouse`, `/api/receipts` (роль `warehouse`) | Сверка заказано/принято, проведение → WMS + 1С через шлюзы, автопродвижение счёта |
| UC-10 | Аналитика и отчёты | **Частично** | `/analytics`, `GET /api/analytics/summary` | Живая сводка (KPI, поставщики, помесячно, аудит). Нет выбора периода, фильтров и выгрузки отчёта |

## 3. Роли и права (ТЗ §3)

| Роль ТЗ | Роль в Keycloak | Политики API | Экран | Статус |
|---|---|---|---|---|
| Руководитель проекта | `manager` | `write` (+ `read`) | каталог, прайсы, спецификации, КП, скидки, проекты, создание согласования и счёта | **Готово** |
| Коммерческий блок | `commercial` | `approve`, `setInvoiceStatus` | `/approval` — решение по КП; стадия счёта «Согласован» (API) | **Готово** |
| Бухгалтерия | `accounting` | `postPayment`, `setInvoiceStatus` | `/invoice` — стадии после «Согласован», вложения | **Готово** |
| Склад | `warehouse` | `receive` | `/warehouse` | **Готово** |
| Администратор | `admin` | все + `admin` | `/audit`, `/users`, `/api/admin/*` | **Частично**: журнал и справочники да; CRUD учёток — в админке Keycloak, не в SPA |
| Аналитик (опционально) | нет отдельной роли | `viewer` читает всё | `/analytics` доступен всем с `read` | **Нет** как отдельная роль |
| Менеджер справочников (опционально) | нет | права совпадают с РП (`write`) | поставщики, производители, номенклатура | **Нет** как отдельная роль; функции есть у `manager`/`admin` |
| (добавлено) Наблюдатель | `viewer` | только `read` | все GET | сверх ТЗ |

Разделение обязанностей соблюдено: РП не согласовывает КП сам себе, бухгалтерия не создаёт заказы,
склад не двигает оплату. Стадию счёта «Согласован» ставит только КБ (`Invoice.ActorMaySet`);
последующие стадии и «Отменён» — бухгалтерия; отказ по роли — 403. Многошагового круга
согласователей NOC нет — одна стадия.

## 4. Функциональные требования

### 4.1 Загрузка Excel (ТЗ §5.1)

| Требование | Статус | Как сделано |
|---|---|---|
| `.xlsx` и `.xls` | **Готово** | ClosedXML + NPOI (OLE2-сигнатура) |
| Проверка структуры, понятная ошибка | **Готово** | Нет обязательных колонок → ошибка в сводке, файл в архиве. Битый файл не даёт 500 |
| Нормализация (регистр, пробелы, ед. изм.) | **Частично** | Trim SKU/имени; единицы измерения **не хранятся** |
| Архив оригинала | **Готово** | `PriceImportUpload.FileContent` (bytea), скачивание |
| Повторная загрузка, история версий | **Готово** | Upsert оффера; каждая загрузка — отдельная запись архива; смена цены → `PriceHistoryEntry` |
| Обязательные поля прайса (артикул, имя, ед. изм., цены с/без НДС) | **Частично** | Обязательны артикул, наименование, цена. Приоритет колонке «без НДС» (НДС считает генератор КП). Ед. изм., ссылка, сертификат, вес, объём, РОЦ/РРЦ, упаковка, статус товара, серия — **не импортируются** |
| Иерархия 1–4 уровня | **Готово** | Собирается со вспомогательных листов, путь через ` / `, фильтр и аналоги |
| Гибкий маппинг колонок (риск §15) | **Готово** | Заголовок ищется в первых 30 строках **на любом листе** (не только первом); колонки — по именам. Из `.xls` переливаются все листы. Путь иерархии длиннее 300 символов сжимается (корень и нижние уровни) |
| Лимит размера файла | **Готово** | ~50 МБ на импорт прайса, ~20 МБ на вложения счёта |

Проверено живым прайсом EKF (`docs/ekf_pricelist_2026-03-30.xlsx`, ~20 тыс. строк).

### 4.2 Структура БД (ТЗ §5.2)

| Сущность ТЗ | В коде | Статус |
|---|---|---|
| Поставщик | `Vendor` (Name, Inn, DefaultLeadTimeDays) | **Частично** — нет контактов, условий, статуса |
| Производитель | `Manufacturer` (Name, Country, IsActive) | **Готово**; у `Product.Manufacturer` строка (денормализация) |
| Номенклатура | `Product` (Sku, Name, Manufacturer, Category) | **Частично** — нет единицы, статуса |
| Прайс / позиция прайса | `PriceImportUpload` + `PriceListItem` | **Готово** в упрощённой модели (цена, срок, остаток, валюта) |
| Скидка | `Discount` | **Готово** |
| Проект | `Project` | **Готово** (карточка; статус/сумма/маржа считаются из Approval/Invoice) |
| Перечень оборудования | `Specification` + `SpecificationItem` | **Готово** |
| КП / позиция КП | `Quote` — **не таблица**, считается на лету; снимок — в `Order`/`InvoiceLine` | **Частично** — нет версий КП как сущности |
| NOC-запись | `Invoice` + `InvoiceLine` + `InvoiceAttachment` | **Готово** как внутренний модуль |
| Журнал событий | `AuditEntry` | **Готово** — HTTP-мутации (middleware) + `ChangesJson` (jsonb) «было → стало» по белому списку сущностей |

Плюс сверх ТЗ: `QuoteOverride`, `Order`/`OrderLine`, `GoodsReceipt`/`GoodsReceiptLine`,
`PriceHistoryEntry`, `OutboxMessage`, `Notification`.

### 4.3 Поиск и сопоставление (ТЗ §5.3)

| Требование | Статус |
|---|---|
| Точное совпадение по артикулу — приоритет | **Готово** (признак `skuExact`, Kind=`ExactSku`) |
| Fuzzy по наименованию | **Готово** — TF-IDF + логистическая регрессия; Meilisearch остаётся источником кандидатов |
| Несколько поставщиков на одну позицию | **Готово** (офферы, 4 стратегии включая ML-актуальность) |
| Синонимы / торговые марки как словарь | **Частично** — нет отдельного словаря (вопрос ТЗ №7); 3-граммы и аналоги категории закрывают опечатки/замены |
| «Не найдено» + КП по остальным | **Готово**; генератор КП ещё подставляет аналог при P≥0.40 |
| Аналоги того же иерархического уровня | **Готово** (`GET /api/products/{id}/analogs` + ML Kind=`Analog`) |
| Уведомление РП о ненайденных | **Частично** — экран сопоставления с P и кнопкой подтверждения; отдельного письма именно про ненайденные нет (общий SMTP-канал — §8) |

### 4.4 Скидки (ТЗ §5.4)

| Требование | Статус |
|---|---|
| Ручной % по вендору и/или производителю | **Готово** |
| Автоприменение в КП | **Готово** (приоритет — скидка поставщика, иначе производителя) |
| Дата действия с/по | **Готово** |
| История изменений скидок в журнале | **Готово** — `Discount` в белом списке `AuditSaveChangesInterceptor` (old/new процента и срока) |
| Цена без НДС и с НДС независимо | **Готово** (ставка `Quote:VatRate`, по умолчанию 20 %) |
| В КП видны исходная и цена со скидкой | **Готово** |

### 4.5 Формирование КП (ТЗ §5.5)

| Требование | Статус |
|---|---|
| 3 варианта: мин. цена / мин. срок / баланс | **Готово** |
| Поля строки: имя, артикул, производитель, поставщик, цены, скидка, срок, причина | **Готово** |
| Сохранение всех версий КП | **Нет** — генерация на лету; фиксация только при заказе/счёте |
| Ручной выбор поставщика в позиции | **Готово** (`QuoteOverride`) |
| Причина выбора | **Готово** (`SelectionReason`) |
| Позиция без данных → «не найдено» | **Готово** |
| Экспорт Excel / PDF | **Готово** |

Алгоритм баланса (открытый вопрос ТЗ №6) зафиксирован: нормировка цены и срока среди
кандидатов позиции, score `wPrice·nPrice + wLead·nLead`, веса по умолчанию 0.5/0.5.

### 4.6 Согласование (ТЗ §5.6)

| Требование | Статус |
|---|---|
| Последовательный маршрут | **Готово** для КП: РП → КБ → Согласовано/Отклонено |
| Уведомление согласующему | **Готово** — сервис Notifications (`/api/notifications`, схема `notifications`): in-app колокольчик и SMTP (`Email:Recipients:commercial`) |
| Утвердить / отклонить с причиной | **Готово** |
| Отклонение → шаг назад, комментарий сохраняется | **Готово** (`resubmit`) |
| Фиксация в журнале | **Готово** — HTTP-мутация + old/new полей `Approval` (перехватчик EF) |

Маршрут счёта NOC (КБ → бухгалтерия) **разделён по ролям** — политика `setInvoiceStatus` и
`Invoice.ActorMaySet` (§7, 10.11).

## 5. NOC (ТЗ §6)

NOC в ТЗ — внешняя система. В курсовой это **внутренний модуль счетов** (`Invoice`),
что прямо разрешено MVP: «может быть в виде шаблона для ручного ввода». Сделано больше
шаблона: полноценный ЖЦ, позиции, документы, связь с приёмкой.

### 5.1 Поля NOC

| Поле ТЗ | Статус | Где |
|---|---|---|
| Номер КП | **Частично** | Номер есть у счёта (`NOC-год-NNN`) и заказа; у самого КП номера нет (КП не сущность) |
| Дата КП | **Частично** | `CreatedAtUtc` согласования/счёта |
| Контрагент | **Частично** | Строка `Customer` со спецификации, без реквизитов |
| Реквизиты контрагента (ИНН, КПП, адрес, банк) | **Нет** | Справочника контрагентов нет |
| Проект | **Готово** | `Project` + связь со спецификацией |
| Позиция, артикул, количество | **Готово** | `InvoiceLine` |
| НМЦ | **Нет** | Отдельного поля нет; в строке — закупочная и цена клиенту |
| Поставщик, производитель | **Готово** | снимок в строке |
| Цена поставщика без/с НДС | **Частично** | Без НДС — `UnitCost`; с НДС считается в КП, в строке счёта не дублируется |
| Скидка % | **Частично** | Учтена в `UnitCost` (уже со скидкой), отдельным полем строки не хранится |
| Сроки поставки | **Частично** | В строке заказа есть; в `InvoiceLine` срока нет |
| Вариант КП | **Готово** | `Approval.Strategy` / `Order.Strategy` |
| Маржа % | **Готово** | `Approval.MarginPercent`, дублируется в шапке счёта |
| Статус согласования / оплаты / поставки / прихода / 1С | **Готово** | Свёрнуто в один enum `InvoiceStatus` на 8 стадий + «Отменён» |
| Прикреплённые документы | **Готово** | `InvoiceAttachment` |

### 5.2 Логика процесса NOC

| Шаг ТЗ | Статус |
|---|---|
| Автосоздание счёта после согласования КП | **Готово** — `DecideAsync` создаёт счёт (автор «Система (авто)»); ручной POST идемпотентен. Два сохранения, не одна транзакция |
| Построчное добавление позиций | **Готово** (снимок генератора КП) |
| Круг согласователей | **Нет** (открытый вопрос ТЗ №2) |
| Уведомление бухгалтерии об оплате | **Готово** — in-app и SMTP по роли `accounting` (сервис Notifications) |
| Оплата + договор | **Готово** (статус + файлы) |
| Проверка договора | **Нет** |
| Ожидание поставки | **Готово** (стадия) |
| Email о прибытии | **Частично** — общее письмо по открытой приёмке роли `warehouse` (колокольчик + SMTP), отдельного шаблона «товар прибыл» нет |
| Фиксация прихода складом | **Готово** |
| Отметка передачи в 1С | **Готово** (автоматом при проведении приёмки) |

## 6. Жизненный цикл (ТЗ §7–8)

| Статус ТЗ | В системе | Статус |
|---|---|---|
| Черновик КП | Генерация на лету, без сущности | **Частично** |
| На согласовании РП / Утверждено РП | `ApprovalStatus.НаСогласованииРП` + `ApplyMarkup` | **Готово** (утверждение РП = задание наценки) |
| В коммерческом блоке | `ВКоммерческомБлоке` | **Готово** |
| КП согласовано / Отклонено | `Согласовано` / `Отклонено` | **Готово** |
| Счёт создан | `InvoiceStatus.Создан` | **Готово** |
| На согласовании (NOC) | `Согласован` | **Частично** — одна стадия без многошагового круга; выставляет только КБ (`commercial`), не бухгалтерия |
| Ожидание оплаты / Оплачено | есть (+ «ЧастичнаяОплата») | **Готово** как статусы, без суммы частичной оплаты |
| Ожидание поставки / Пришёл на склад / Отражено в 1С | есть | **Готово**; две последние стадии выставляет приёмка |
| Отклонено → черновик | resubmit согласования | **Готово** для КП; для счёта — `Отменён` |

Параллельно живёт ЖЦ **заказа** (`Draft → Placed → Confirmed → Shipped → Completed` / `Cancelled`) —
в ТЗ его как отдельной сущности нет, это срез «поставка».

## 7. Журнал, ошибки, безопасность

### Журнал (ТЗ §9)

| Требование | Статус |
|---|---|
| Значимые события | **Частично** — все HTTP-мутации (middleware) плюс доменные изменения белого списка (перехватчик EF) |
| Дата UTC, пользователь, действие, объект, old/new | **Готово** для Discount, Order, Invoice, Approval, GoodsReceipt, PriceListItem (изменения существующих; новые офферы импорта не пишутся). Поле `AuditEntry.ChangesJson` (jsonb) |
| Доступ только админу (аналитику — ограничено) | **Готово** для админа; у аналитика отдельного урезанного журнала нет |
| Нельзя править/удалять | **Готово** (нет API на изменение) |
| Хранение ≥ 3 лет | **Готово** (`Audit:RetentionDays = 1095`, фоновая очистка) |
| Оповещения на критичные события | **Частично** — in-app и SMTP по открытым документам, не отдельное письмо «скидка изменилась» |

### Ошибки (ТЗ §10)

| Ситуация | Статус |
|---|---|
| Некорректный Excel | **Готово** |
| Позиция не найдена | **Готово** |
| Дубли артикулов в прайсе | **Готово** (предупреждение со строками) |
| Нет цены/срока | **Частично** — без цены строка в ошибках; срок фолбэчится на дефолт поставщика |
| Ошибка интеграции NOC/1С + ретрай + письмо админу | **Нет** (мок почти всегда успешен; ERPNext вернёт ошибку в лог, без очереди повтора) |
| Превышение размера файла | **Готово** |

### Безопасность (ТЗ §11)

| Требование | Статус |
|---|---|
| SSO или форма входа | **Готово** — Keycloak, OIDC Authorization Code + PKCE |
| RBAC | **Готово** |
| Таймаут сессии 30 мин | **Нет** как явное требование; живут дефолты Keycloak + токен в `localStorage` |
| HTTPS/TLS | **Частично** — `UseHttpsRedirection` в Api, локальный стенд на HTTP |
| Хэш паролей | **Готово** — пароли в Keycloak, не в нашем приложении |
| Журнал аудита только админу | **Готово** |
| Экспорт Excel/PDF авторизованным | **Готово** (`read`) |
| Файлы прайсов с контролем доступа | **Частично** — в БД за JWT; отдельного объектного хранилища нет |

## 8. Интеграции (ТЗ §12)

| Система | Требование ТЗ | Факт |
|---|---|---|
| NOC | обязательно, API/БД | **Внутренний модуль** счетов. Внешнего NOC нет — осознанное решение MVP |
| 1С | обязательно | **Мок** `MockAccountingGateway`. Есть выключаемый адаптер `ErpNextAccountingGateway` (`ExternalAccounting:Mode=ErpNext`) — не 1С, но тот же контракт `IAccountingGateway` |
| WMS | вместе с приёмкой | **Мок** `MockWarehouseGateway` |
| Email / мессенджер | обязательно | **Готово** для email: сервис Notifications, `IEmailSender` / SMTP / MailHog (`:8025`). Мессенджера нет. У монолита на хосте `Email:Enabled=false`; почту шлёт Notifications |
| Excel | MVP обязательно | **Готово** |
| AD / LDAP | желательно | **Частично** — Keycloak умеет federation, в стенде — локальные учётки realm `procurement`. Регистрация/вход и список пользователей — отдельный процесс Auth за шлюзом |

Статус шлюзов 1С/WMS: `GET /api/integration/status` (монолит). Экран `/settings` частично живой (карточки 1С/WMS),
остальные вкладки — макет.

Внутренний контур (не системы из §12 ТЗ, но закрывает разнесение нагрузки): Docker-SPA ходит
в YARP-шлюз (`:5160`). Вынесены Auth, Catalog, Quoting, Commercial, Ordering, Logistics и
Notifications. Подробности — [ARCHITECTURE.md](ARCHITECTURE.md) §3.

## 9. Нефункциональные требования (ТЗ §13)

| Требование | Статус | Комментарий |

| Хранение файлов 5 лет | **Частично** | Файлы в Postgres, отдельной политики 5 лет нет (аудит — 3 года) |
| Бэкап БД ежедневно | **Нет** в репозитории | Volume Docker, бэкап не автоматизирован |
| Chrome, Edge | **Готово** (SPA) | Отдельной матрицы браузеров нет |
| UI на русском | **Готово** |
| Журнал 3 года | **Готово** |

Наблюдаемость сверх ТЗ: Serilog, OpenTelemetry → Grafana (Tempo/Loki/Prometheus); сквозные трассы
шлюз → сервис → (NATS) → Worker. У каждого процесса своё имя `service`.

## 13. Что ещё не закрыто (имеющий смысл остаток)

Упорядочено по влиянию на защиту и на «полноту ТЗ». Закрыто этой ночью и вычеркнуто:
10.11 (маршрут КБ → бухгалтерия), автосоздание счёта (UC-07), old/new в аудите (§9),
email (ТЗ §12, SMTP/MailHog).

1. **Справочник контрагентов и НМЦ** — поля, которые хорошо смотрятся на защите карточки счёта.
2. **Версии КП как сущность** — сейчас «история КП» = история заказов/счетов.
3. **Настройки** — убрать макет или честно спрятать мёртвые вкладки.
4. **Cutover микросервисов 12.5–12.7 закрыт** — маршруты шлюза, перенос `public.*` (`tools/cutover/`),
   соседи в Compose. Остаток: Vite на Gateway, retail vs схема catalog, копии в монолите (см. ARCHITECTURE §3).
5. **Круг согласователей NOC** — одна стадия «Согласован» (её ставит КБ), не цепочка лиц.
6. **Пояснительная записка (этап 11)** — черновик собран (`docs/zapiska/`); руками — титул,
   скриншоты, блок-схемы.

Не стоит обещать к защите, если нет времени: синонимы номенклатуры, настоящая 1С, мобильный UI,
KPI со целевыми значениями, ежедневный бэкап, HA.
