анализа поставщиков и формирования коммерческих предложений
Версия 1.0 (Черновик)
Дата составления: 24.04.2026
Статус: Требует согласования с заказчиком
1. Описание продукта
Настоящее техническое задание описывает корпоративную информационную систему (далее — Система), предназначенную для автоматизации процессов подбора оборудования, анализа предложений поставщиков, формирования коммерческих предложений (КП) и ведения закупочного процесса от момента запроса до прихода товара на склад и отражения в 1С.
Система интегрируется с NOC (внутренним инструментом ведения заказов и согласований) и бухгалтерской системой 1С.
⚠ Наименование системы требует согласования с заказчиком.
1.1. Предпосылки создания
В подразделении регулярно реализуются проекты, совмещающие проектирование и поставку оборудования. Перечни оборудования по таким проектам могут быть значительными по объёму. При существующем подходе руководитель проекта (РП) тратит значительное время на анализ поставщиков, что приводит к:
недостаточной глубине анализа рынка;
выбору единственного поставщика без сравнительного анализа;
завышению себестоимости закупки;
снижению маржинальности проектов;
падению процента выигранных тендеров.
2. Цели и задачи системы
2.1. Цели
Снижение себестоимости закупки оборудования.
Повышение качества и глубины анализа рынка поставщиков.
Сокращение временных затрат РП на подбор поставщиков.
Увеличение процента выигранных тендеров.
Обеспечение сквозной прозрачности процесса от формирования КП до прихода товара на склад.
2.2. Задачи системы
Загрузка и хранение прайс-листов поставщиков и производителей в единой базе данных.
Автоматическое сопоставление позиций проекта с данными БД.
Формирование нескольких альтернативных вариантов КП.
Поддержка ручного ввода скидок по вендорам и производителям.
Передача согласованных данных в коммерческий блок для расчёта маржинальности.
Автоматическое формирование данных для NOC после согласования КП.
Ведение статусов процесса: согласование → оплата → поставка → склад → 1С.

5. Функциональные требования
5.1. Требования к загрузке Excel
Система принимает файлы форматов .xlsx, .xls.
При загрузке выполняется проверка структуры файла на соответствие ожидаемому формату.
При несоответствии структуры система выводит понятное сообщение об ошибке с указанием проблемных столбцов.
Поддерживается нормализация данных: приведение к единому регистру, удаление пробелов, стандартизация единиц измерения.
Система сохраняет оригинальный файл в архиве загрузок.
Поддерживается повторная загрузка (обновление) прайса — данные обновляются, история предыдущих версий сохраняется.

5.3. Требования к поиску и сопоставлению номенклатуры
Сопоставление позиций проекта с позициями БД выполняется по артикулу (точное совпадение — приоритет).
При отсутствии точного совпадения применяется нечёткий поиск по наименованию (fuzzy matching) с настраиваемым порогом схожести.
Система обрабатывает дубли: если одна позиция присутствует у нескольких поставщиков, все варианты отображаются для сравнения.
Система обрабатывает разные наименования одной позиции (синонимы, торговые марки) — алгоритм требует уточнения при проектировании.
Если позиция не найдена ни у одного поставщика, система фиксирует её как «не найдено» и уведомляет РП.
Система предлагает аналоги из того же иерархического уровня номенклатуры при отсутствии точного совпадения.
⚠ Алгоритм нечёткого сопоставления (fuzzy matching) требует проработки при техническом проектировании. Возможные решения: Levenshtein distance, TF-IDF, векторный поиск. Выбор — на усмотрение разработчика с согласованием заказчика.
5.4. Требования к скидкам
РП вручную вводит процент скидки по каждому вендору и/или производителю.
Скидки хранятся в системе и применяются автоматически при формировании КП.
Скидки имеют дату действия (с/по) — требует уточнения.
История изменения скидок сохраняется в журнале.
Скидка применяется к базовой цене поставщика без НДС и к цене с НДС независимо.
В КП отображается как исходная цена, так и цена со скидкой.
5.5. Требования к формированию КП
Система формирует 3 варианта КП для каждого проекта:
Вариант КП
Логика формирования
Приоритет выбора

Себестоимость
По минимальному сроку поставки
По каждой позиции выбирается поставщик с минимальным сроком поставки
Скорость

Баланс
Для каждой позиции КП отображаются: наименование, артикул, производитель, поставщик, цена (с/без НДС), скидка, итоговая цена, срок поставки, причина выбора варианта.
Система сохраняет все версии КП с историей изменений.
РП может вручную скорректировать выбор поставщика для отдельной позиции.
Система показывает причину выбора варианта (почему выбран именно этот поставщик).
Если по позиции нет данных — фиксируется статус «не найдено», КП формируется по оставшимся позициям.
5.6. Требования к согласованию
Согласование выполняется в рамках последовательного маршрута (см. таблицу этапов согласования в разделе 6).
На каждом этапе согласующий получает уведомление (email / внутреннее уведомление — способ доставки требует уточнения).
Согласующий может утвердить или отклонить с указанием причины.
При отклонении процесс возвращается на шаг назад с сохранением комментария.
Все действия по согласованию фиксируются в журнале с указанием пользователя, даты и времени.

6.2. Логика процесса в NOC
После согласования КП система автоматически инициирует создание записи в NOC по следующему алгоритму:
Создаётся счёт с реквизитами контрагента (из справочника контрагентов или введённых вручную).
В счёт построчно добавляются все позиции утверждённого варианта КП с указанием количества и НМЦ.
Запускается круг согласователей (состав и порядок требуют уточнения у заказчика).
После прохождения круга согласования бухгалтерия получает уведомление об оплате.
Бухгалтерия оплачивает счёт, прикладывает договор и документацию.
Выполняется проверка договора с поставщиком (ответственный — требует уточнения).
После оплаты система переходит в статус ожидания поставки.
На электронную почту ответственного поступает уведомление о прибытии товара (источник уведомления требует уточнения).
Склад фиксирует факт прихода товара в системе.
Склад передаёт данные в 1С, фиксирует отметку о передаче в системе.

9. Требования к журналированию
Система ведёт журнал всех значимых событий: загрузка файлов, изменение скидок, формирование КП, смена статусов, действия пользователей.
В каждой записи журнала фиксируется: дата и время (UTC), пользователь, тип действия, объект, старое и новое значение.
Журнал доступен администратору системы и, в ограниченном объёме, аналитику.
Журнал не редактируется и не удаляется пользователями.
Срок хранения журнала — требует уточнения (рекомендуется не менее 3 лет).
Для критичных событий (изменение скидок, смена статуса согласования) предусмотрена система оповещений — способ и адресаты требуют уточнения.

11. Требования к безопасности и доступам
Аутентификация пользователей: корпоративная SSO (Single Sign-On) или отдельная форма входа — способ требует уточнения.
Авторизация на основе ролей (RBAC): каждый пользователь имеет только необходимые права.
Все сессии имеют тайм-аут — конкретное значение требует уточнения (рекомендуется 30 минут бездействия).
Передача данных — только по защищённому протоколу (HTTPS/TLS).
Пароли хранятся в хэшированном виде (bcrypt или аналог) — если используется отдельная аутентификация.
Доступ к журналам аудита — только у администратора.
Экспорт данных в Excel/PDF — только для авторизованных ролей.
Физические файлы прайсов хранятся в защищённом хранилище с контролем доступа.
⚠ Требования к безопасности должны быть согласованы с ИБ-службой организации перед началом разработки.
