# Руководство пользователя

Короткий сквозной прогон стенда: заявка → подбор → КП → согласование → счёт → приёмка. Роли, политики и статусы взяты из кода, не из ТЗ. Подписи кнопок — как на экранах `frontend/src/pages`.

Состав экранов и меню — `docs/UI.md`. Матрица API — `docs/API.md`. Жизненные циклы — `docs/ARCHITECTURE.md` §7.

> Проверено на поднятом стенде: статусы счёта сверены с `Invoice.LinearFlow`, переходы заказа — с `Order.Transitions`, производные статусы проекта — с `ProjectService.Resolve`, адрес сида каталога — с `ECatalog.tsx`. Расхождений с кодом не найдено. Отдельно отмечены три места, где следование инструкции упрётся в известные дефекты импорта, — они помечены значком ⚠.

## 1. Адреса стенда

| Что | Адрес |
|---|---|
| Кабинет (React) | http://localhost:5173 |
| Gateway (вход `/api` в Docker) | http://localhost:5160 |
| API монолита (хост / Scalar) | http://localhost:5165, Scalar `/scalar` |
| Auth-сервис | http://localhost:5167 |
| Keycloak | http://localhost:8088 (админка `admin` / `admin`) |
| Grafana (трассы, логи, метрики) | http://localhost:3000 |
| MailHog (письма стенда) | http://localhost:8025 (SMTP 1025) |

В Docker SPA ходит same-origin `/api` → nginx → шлюз `:5160` (каталог — Catalog, остальное catch-all — монолит). На хосте Vite проксирует `/api/auth` и `/api/users` на Auth `:5167`, остальной `/api` — на монолит `:5165` (шлюз не участвует).

Наблюдаемость собрана в один контейнер `grafana/otel-lgtm`: Tempo хранит трассы, Loki — логи, Prometheus — метрики, Grafana показывает всё это связанно. Вход без пароля. Прежний Jaeger убран: он умел только трассы, а логи и метрики уходили в никуда.

Запуск стека — `README.md` («Установка и запуск»). Этот документ предполагает, что фронт, Api, Auth, Keycloak и Postgres уже подняты. Письма видны в MailHog только если поднят Compose (`Email__Enabled=true` у `api`); на хосте email по умолчанию выключен.

Вход в кабинет — форма «Вход в кабинет» (`pages/AuthScreen.tsx`), не редирект Keycloak. Запрос идёт на `POST /api/auth/login` (сервис Auth). Ссылка «Войти через учётку организации» открывает OIDC-редирект — для сценария ниже не нужна.

## 2. Учётки

Пароль совпадает с логином. Realm `procurement`, шесть ролей (`README.md`, `keycloak/realm-procurement.json`).

| Логин | Роль Keycloak | После входа открывается | Зачем в этом сценарии |
|---|---|---|---|
| `manager` | РП | `/` Проекты | заявка, подбор, КП, наценка, заказ; счёт создаётся сам при согласовании |
| `commercial` | КБ | `/approval` Маржа | согласовать или отклонить КП (это же создаёт счёт); стадия счёта «Согласован» — через API |
| `accounting` | Бухгалтерия | `/invoice` Счета | стадии после «Согласован», документы |
| `warehouse` | Склад | `/warehouse` Склад | приёмка |
| `admin` | Администратор | `/` | сид каталога, журнал, пользователи |
| `viewer` | Наблюдатель | `/` | только чтение; в сценарии не участвует |

Политики API (`src/ProcurementSystem.Api/Program.cs`):

| Политика | Роли | Что закрывает в этом сценарии |
|---|---|---|
| `write` | admin, manager | заявка, подбор apply, КП-override, согласование/наценка/resubmit, заказ, создание счёта |
| `approve` | admin, commercial | `POST /api/approvals/{id}/decision` |
| `setInvoiceStatus` | admin, commercial, accounting | `POST /api/invoices/{id}/status` («Согласован» — КБ, дальше — бухгалтерия) |
| `postPayment` | admin, accounting | вложения счёта |
| `receive` | admin, warehouse | приёмка |
| `read` | все шесть | GET-ы и генерация КП |

Меню кабинета уже API GET: например `warehouse` не видит «Маржа» и «Счета» (`frontend/src/auth/access.ts`). API при живом токене всё равно отдаст `GET /api/invoices` — режет SPA.

Регистрация с экрана входа создаёт учётку с ролью `viewer` (`Auth/Keycloak/KeycloakOptions.cs`, `DefaultRole`). Для сценария ниже регистрироваться не нужно.

## 3. Что должно быть в каталоге до старта

Подбор и КП читают `Products` и `PriceListItems`. Пустой каталог: на сопоставлении «Нет гипотезы», в КП строки «нет предложений», заказ из КП вернёт ошибку «В КП нет сопоставленных позиций».

На текущем стенде каталог уже наполнен — синтетический корпус плюс импортированные прайсы реальных производителей:

| Поставщик | Позиций | Источник |
|---|---|---|
| ОВЕН | 78 934 | живой прайс с сайта |
| Крепиз | 30 722 | живой прайс, два файла |
| Meyertec | 1 292 | живой прайс |
| `ПЛ-001`…`ПЛ-120` | ~40 700 | синтетический корпус для ML |

Итого около 115 тысяч товаров. Для сценария ниже этого более чем достаточно, сид запускать не нужно.

Проверка: войдите как `manager` → меню **Каталог** (`/ecatalog`). Если карточек нет:

1. Выйдите, войдите как `admin` / `admin`.
2. Снова **Каталог**. У admin есть кнопка сида (`POST /api/admin/seed?vendors=20&products=800&maxOffersPerProduct=3` в `ECatalog.tsx`).
3. Дождитесь появления карточек с ценами.
4. Выйдите, дальше работайте как `manager`.

Альтернатива объёма для ML: под `admin` экран **Прайсы** → «Корпус для сопоставления» (`POST /api/pricelist/seed-corpus`). Создаёт кривую заявку и сразу предлагает открыть сопоставление.

Импортёр сжимает путь иерархии длиннее 300 символов (корень и нижние уровни), ищет лист с товарами по заголовкам (не только первый) и из `.xls` переливает все листы. Файл `docs/ekf_pricelist_2026-03-30.xlsx` больше не должен падать на `varchar(300)`. На показе всё равно удобнее уже наполненный каталог, чем ждать импорт ~20 тыс. строк.

Скидки не обязательны. Если завести правило на **Скидки**, процент появится в колонке «Скидка» листа КП (применяет генератор, не кнопка).

## 4. Статусы, которые встретятся

Не выдуманы: enum и методы сущностей Domain. Полные таблицы — `docs/DATA_MODEL.md` § «Ключевые справочники статусов».

**Заявка** (`Specification`) статуса документа не имеет. На экране заявки у строки: «Сопоставлено» / «Не сопоставлено» — это наличие `ProductId`.

**Согласование** (`Domain/Commercial/Approval.cs`):

| Статус в API | Подпись на экране «Маржа» | Как получается |
|---|---|---|
| `НаСогласованииРП` | На согласовании РП | `POST /api/approvals` |
| `ВКоммерческомБлоке` | В коммерческом блоке | «Отправить в КБ» / «Пересчитать» → `POST .../margin` |
| `Согласовано` | Согласовано | «Согласовать» → `POST .../decision` `{ approved: true }` |
| `Отклонено` | Отклонено | «Отклонить» |

Из `Отклонено` РП жмёт «Отправить на доработку повторно» → снова `НаСогласованииРП`. Комментарий КБ не стирается.

**Счёт** (`Domain/Commercial/Invoice.cs`, `LinearFlow`):

`Создан → Согласован → ОжиданиеОплаты → ЧастичнаяОплата → Оплачено → ОжиданиеПоставки → ПришёлНаСклад → ОтраженоВ1С`

Плюс `Отменён` из любого статуса, кроме уже `Отменён` и `ОтраженоВ1С`. Пропуск стадии даёт HTTP 409. «Согласован» ставит только КБ (`commercial` / admin); бухгалтерия на эту стадию получит 403. Дальше и «Отменён» — бухгалтерия. Счёт при согласовании КП создаётся сам (автор «Система (авто)»).

**Заказ** (`Domain/Ordering/Order.cs`):

`Draft → Placed → Confirmed → Shipped → Completed`, с `Cancelled` из `Draft`/`Placed`/`Confirmed`. Подписи на экране: Черновик / Размещён / Подтверждён / Отгружен / Завершён / Отменён (`frontend/src/data/orders.ts`).

**Приёмка** (`Domain/Logistics/GoodsReceipt.cs`): `Черновик` → `Проведено`. Значение `Отменена` в enum есть, кнопки и эндпоинта нет.

**Карточка проекта** показывает *производный* статус (`ProjectService.Resolve`): «Черновик КП», «Согласование РП», «В коммерческом блоке», «КП согласовано», затем стадии счёта укрупнённо («Счёт создан», «Ожидание оплаты», …). Это не отдельная таблица статусов проекта.

## 5. Сценарий: `manager`

Цель: заявка с сопоставленными позициями, четыре листа КП, согласование с наценкой, заказ-снимок. Счёт после решения КБ создаётся сам — менеджеру жать «Новый счёт» не нужно (кнопка остаётся как запасной путь, POST идемпотентен). Заказ менеджер оформляет сам: без него складу не из чего делать приёмку.

### 5.1. Войти

1. http://localhost:5173
2. Вкладка **Вход**. Логин `manager`, пароль `manager`, **Войти**.
3. Должны открыться **Проекты** (кикер «тендеры»). В сайдбаре группа «Контур КП»: Проекты, Прайсы, Каталог, Заявки, Заказы.

### 5.2. Создать заявку

1. Меню **Заявки** (`/specifications`).
2. **Новая спецификация**. Поля: «Название» (обязательно), «Заказчик» (необязательно). **Создать**.
3. Откроется карточка заявки. Позиций 0, сопоставлено 0.

Импорт Excel на том же экране: **Импорт Excel**, файл `.xlsx` (колонки артикул / наименование / количество). Название для импорта берётся из формы, если её открыть, иначе — имя файла. После успеха — та же карточка с позициями. Часть строк может быть уже с «Сопоставлено», если артикул совпал.

### 5.3. Набрать позиции

На карточке заявки блок «Добавить позицию»:

- Печать артикула или имени (≥ 2 символов) → подсказка `GET /api/catalog/suggest`. Enter / клик по строке добавляет **сопоставленную** позицию.
- **Как есть** — строка без `ProductId`, её доберёт сопоставление.

Нужны хотя бы 2–3 позиции, у которых в каталоге есть офферы нескольких поставщиков — иначе четыре листа КП совпадут.

Альтернатива: **Каталог** → в карточку → в корзину → в ящике корзины оформить в новую заявку или в существующую (`ecatalog/shared.tsx`). Заголовок новой заявки: `Подборка из каталога · <дата>`.

### 5.4. Запустить подбор

1. На карточке заявки кнопка **Сопоставление** (`/specifications/:id/match`).
2. Появится разбор: «Точный SKU», «По имени», «Аналог», «Нет гипотезы»; у гипотезы — P и причина.
3. Если строка «Ещё без товара» и P ≥ 0.5 — **Применить лучшие (P≥0.5)**. Статус строки станет «В заявке».
4. Если P < 0.5 — жёлтая пометка «ниже порога 0.5»; кнопка **взять** на нужной гипотезе.
5. Когда сопоставлено достаточно строк — **Перейти к КП**.

Алгоритм — `docs/ML_MATCHING.md`. Экран не меняет статус документа: пишет `SpecificationItems.ProductId`.

### 5.5. Собрать КП

1. Экран **Варианты КП** (`/specifications/:id/quote`). Четыре плитки: «Себестоимость», «Скорость», «Баланс», «Актуальность» (`STRATEGY_META` в `frontend/src/data/orders.ts`).
2. Клик по плитке выбирает лист (метка «выбран»). Внизу — позиции, поставщик, скидка, срок, итог без НДС и с НДС.
3. Строка без оффера подсвечена, в поставщике — «нет предложений». В итог она не входит.
4. По желанию **Детальный КП**: разворот строки → другой поставщик. Это `POST .../override`; в причине выбора будет «Выбрано вручную».
5. **Выгрузить в Excel** / **PDF** — скачивание выбранного листа. На заказ и согласование не влияет.

Зафиксировать выбранный лист двумя независимыми действиями:

| Кнопка | Что происходит | Статус |
|---|---|---|
| **Передать в КБ** | `POST /api/approvals` с `markupPercent: 10` и выбранной стратегией | согласование `НаСогласованииРП`; переход на `/approval?id=...` |
| **Оформить заказ** | `POST /api/orders/from-quote` | заказ `Draft`, номер вида `ORD-yyyyMMdd-HHmmss`; переход на карточку заказа. Остаток оффера уменьшается |

Сделайте **оба**. Порядок любой. Без заказа складу нечего принимать. Без согласования счёт не появится.

Наценка 10 % при «Передать в КБ» — константа фронта. Её меняют на экране «Маржа».

### 5.6. Наценка и передача в КБ

Если нажали «Передать в КБ», вы уже на **Маржа**. Иначе меню **Маржа** (`/approval`), клик по строке заявки.

1. Блоки: Себестоимость → Наценка → Цена клиенту.
2. Ползунок 0…200 % (или число). Маржа пересчитывается на экране сразу, в БД — после кнопки.
3. **Отправить в КБ** (если статус «На согласовании РП») или **Пересчитать** (если уже в КБ).
4. Статус документа: **В коммерческом блоке**. Маршрут слева: шаг 2 «на рассмотрении».

РП **не видит** кнопки «Согласовать» / «Отклонить» (`canApprove` только у commercial и admin).

### 5.7. Заказ (если ещё не оформили)

**Заказы** → карточка. Статус **Черновик**. Кнопки в шапке: **→ Размещён** и **Отменить**. Для приёмки достаточно `Draft`: склад создаёт приёмку из любого существующего заказа, проверки статуса заказа в `WarehouseService.CreateFromOrderAsync` нет.

Двигать ЖЦ заказа в этом прогоне не обязательно. Если двигать — только соседний статус, иначе 409.

Выйдите (меню пользователя в шапке кабинета).

## 6. Сценарий: `commercial`

1. Войти `commercial` / `commercial`. Сразу экран **Маржа** (`homePath` в `access.ts`).
2. В таблице — согласование менеджера, статус «В коммерческом блоке» (или «На согласовании РП», если РП не нажал «Отправить в КБ»).
3. Клик по строке. Себестоимость, наценка, цена клиенту. Ползунка наценки нет (`canWrite` у commercial нет).
4. Поле «Комментарий (необязательно)».
5. **Согласовать**. Статус: **Согласовано**. Маршрут — все три шага зелёные. В той же операции создаётся счёт NOC (`CreatedBy` = «Система (авто)», статус **Создан**). Согласование и счёт пишутся двумя сохранениями: если генерация счёта упадёт, КП уже согласовано — досоздайте счёт вручную как `manager` («Новый счёт», тот же ApprovalId, второй счёт не появится).

**Отклонить** ставит **Отклонено** и счёт не создаёт. Тогда выйдите, войдите как `manager`, откройте ту же карточку, **Отправить на доработку повторно**, поправьте наценку, снова **Отправить в КБ**, и вернитесь сюда.

В монолите `DecideAsync` не требует статуса `ВКоммерческомБлоке`: commercial может согласовать документ сразу после создания. Штатный кадр защиты — сначала наценка РП, потом решение КБ.

Кнопки «Новое согласование» у commercial нет. Экран `/invoice` у commercial в меню нет (`access.ts`: admin / manager / accounting) — стадию «Согласован» на карточке счёта в кабинете ставит `admin` (у него `canApprove` и доступ к экрану). Commercial через Scalar: `POST /api/invoices/{id}/status` `{ "status": "Согласован" }`.

Перед бухгалтерией поставьте «Согласован»: выйдите, войдите как `admin` / `admin`, **Счета**, клик по только что созданному, кнопка **Согласован**.

Выйдите.

## 7. Сценарий: `accounting`

1. Войти `accounting` / `accounting`. Сразу **Счета**.
2. Кнопки «Новый счёт» нет (`canWrite` нет). Счёт уже должен быть: его создало согласование КБ. Если списка нет — КБ ещё не нажал «Согласовать», либо генерация счёта упала (тогда запасной путь: `manager` → **Новый счёт**, POST идемпотентен).
3. Клик по счёту. Если статус ещё **Создан**, кнопки «Следующая стадия: Согласован» **нет** (`canAdvance` требует `canApprove`). Бухгалтерия эту стадию не ставит.
4. Если вызвать API всё равно (`POST /api/invoices/{id}/status` `{ "status": "Согласован" }`) — **403** «Стадию «Согласован» выставляет только коммерческий блок». На показе стадию уже поставил `admin` в конце шага 6.
5. Позиции — снимок КП с наценкой. **Прикрепить документ** — любой файл (политика `postPayment`, лимит ~20 МБ).
6. Кнопка **Следующая стадия: …** двигает **ровно на один** шаг. Для сшивки со складом нужно дойти до **Ожидание поставки**:

| Сейчас | После нажатия |
|---|---|
| Согласован | Ожидание оплаты |
| Ожидание оплаты | Частичная оплата |
| Частичная оплата | Оплачено |
| Оплачено | Ожидание поставки |

Остановитесь на **Ожидание поставки**. Стадии «Пришёл на склад» и «Отражено в 1С» проведёт приёмка. Если нажать их вручную до склада — приёмка уже не найдёт счёт в `ОжиданиеПоставки` и молча не продвинет его (`WarehouseService.AdvanceLinkedInvoiceAsync`).

**Отменить счёт** доступна, пока статус не `ОтраженоВ1С` и не `Отменён` (`canPostPayment`). Для сценария не жмите. Commercial «Отменён» через API тоже получит 403 («Последующие стадии счёта выставляет бухгалтерия»).

Попытка перескочить стадию (Scalar / чужой клиент) → 409 «Недопустимый переход статуса».

Выйдите.

## 8. Сценарий: `warehouse`

1. Войти `warehouse` / `warehouse`. Сразу **Склад**.
2. Выпадающий список заказов (все `GET /api/orders`, без фильтра по статусу). Выберите заказ менеджера (`ORD-…`).
3. **Создать приёмку**. Статус **Черновик**. `ReceivedQty` по строкам равен заказанному.
4. При расхождении измените «Принято» и уберите фокус с поля (запрос уходит на `blur`). «Состояние»: В норме / Недостача / Излишек. Колонка «Расхождение» = принято − заказано.
5. **Провести приёмку**.
6. Статус: **Проведено**. Полоса «Выгружено во внешние системы»: WMS всегда `MockWarehouseGateway` (ссылка вида `WMS-yyyyMMdd-…`). 1С по умолчанию `MockAccountingGateway` (`1С-yyyyMMdd-…`); `ErpNextAccountingGateway` включается только если в конфиге `ExternalAccounting:Mode=ErpNext` (`Infrastructure/Logistics/LogisticsModule.cs`). Повторно провести нельзя: «Приёмка уже проведена или отменена».

Если счёт был в **Ожидание поставки**, он станет **Пришёл на склад**, затем **Отражено в 1С**. Проверка: выйти, войти как `accounting` или `manager`, открыть **Счета**.

Повтор «Создать приёмку» на тот же заказ не плодит документ: вернётся уже существующий.

## 9. Что должно получиться в конце

| Документ | Где смотреть | Ожидаемый статус |
|---|---|---|
| Заявка | Заявки → карточка | строки «Сопоставлено» |
| Согласование | Маржа | **Согласовано** |
| Счёт | Счета | **Отражено в 1С** (если склад провёл приёмку при счёте в «Ожидание поставки») |
| Заказ | Заказы | **Черновик**, если ЖЦ не двигали |
| Приёмка | Склад | **Проведено**, заполнены WMS/1С |
| Проект (если привязали заявку) | Проекты | производный «Отражено в 1С» |

Колокольчик в шапке: при чтении ленты сервис досоздаёт уведомления (открытые согласования → роль `commercial`, незакрытые счета → `accounting`, заказы в работе → `manager`, черновики приёмок → `warehouse`). После проведения приёмки новое «ожидает проведения» по этому документу не появится.

Те же события уходят письмом, если email включён (Compose: MailHog http://localhost:8025, адреса `Email:Recipients:{role}` — `commercial@procurement.local` и т.д.). На хосте `Email:Enabled=false`, писем не будет.

## 10. Типичные отказы (как в коде, не «если что-то пошло не так»)

| Что сделали | Что увидите | Почему |
|---|---|---|
| `commercial` жмёт «Создать согласование» | кнопки нет | политика `write` |
| `manager` жмёт «Согласовать» | кнопок решения нет | политика `approve` |
| `accounting` создаёт счёт | кнопки «Новый счёт» нет | `write` |
| `manager` двигает стадию счёта | кнопок «Следующая стадия» нет | `setInvoiceStatus` + `canApprove`/`canPostPayment` |
| `accounting` ставит «Согласован» (API) | 403 «Стадию «Согласован» выставляет только коммерческий блок» | `Invoice.ActorMaySet` |
| `commercial` ставит «ОжиданиеОплаты» / «Отменён» (API) | 403 «Последующие стадии счёта выставляет бухгалтерия» | `Invoice.ActorMaySet` |
| Счёт из несогласованного КП (API) | 409 «Счёт можно создать только из согласованного КП» | `InvoiceCommandService` |
| Пропуск стадии счёта | 409 «Недопустимый переход…» | `Invoice.CanTransitionTo` |
| Заказ из КП без сопоставленных строк | 400 «В КП нет сопоставленных позиций» | `OrdersController` |
| `Draft → Confirmed` у заказа | 409 | нет такого ребра в `Order.Transitions` |
| Приёмка не `Черновик`, правка кол-ва | 409 «Приёмка уже проведена или отменена» | `WarehouseService.SetReceivedAsync` |
| Каталог пуст | сопоставление пустое, КП без поставщиков | нет `PriceListItems` |
| Счёт не доведён до «Ожидание поставки» | после склада счёт остался на прежней стадии | автосшивка ищет только этот статус |

Экран **403** (`pages/Forbidden.tsx`) — роль не в матрице `access.ts` (например `warehouse` открыл `/approval` вручную). Это не ответ API.

## 11. Соседние экраны, которые сценарий не требует

Их не нужно проходить, чтобы закрыть контур, но они живые:

- **Прайсы** — импорт Excel, архив, ручной оффер, история цен. Лист с товарами ищется по заголовкам (не только первый); из `.xls` переливаются все листы; путь иерархии длиннее 300 символов сжимается. Книги со встроенными фотографиями товаров ClosedXML по-прежнему может не открыть (`Picture names cannot be empty`; в тестах этот кейс пропущен).
- **Номенклатура / Поставщики / Производители / Скидки** — справочники РП.
- **Розница** — съём витрин и запись в тот же каталог.
- **Сводка** — KPI без фильтра периода.
- **Журнал / Люди / Настройки** — admin. Журнал показывает «было → стало» по белому списку сущностей. «Люди» читает Keycloak Admin API (`GET /api/users` на Auth). «Настройки»: рабочие тема и статус шлюзов; четыре карточки сервисов — макет.
- **MailHog** — http://localhost:8025, если стенд в Docker.

Scalar (http://localhost:5165/scalar; в Docker те же пути через шлюз `:5160`): тот же JWT, что у кабинета (вкладка Authentication → Bearer). Для разбора 403/409 удобнее, чем UI.

## 12. Выход и смена роли

Кабинет не держит несколько ролей в одной сессии. Выход — иконка в шапке сайдбара (`title="Выйти"`, `auth.signoutRedirect()` в `components/Shell.tsx`): браузер уходит в Keycloak logout и возвращается на форму входа. Дальше другой логин. Токены пишет `AuthScreen` в user manager OIDC (`oidc-client-ts`). Не открывайте два кабинета в одной сессии браузера под разными ролями — перезапишете токен.
