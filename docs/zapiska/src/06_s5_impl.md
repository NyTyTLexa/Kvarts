# 5 Программная реализация системы

Исходный код лежит в одном репозитории, поскольку границы контекстов уже проведены проектами решения, а вынос в отдельные процессы ещё следует шаблону Strangler Fig из раздела 4 [14]. Общие параметры C#-проектов (nullable-ссылки, неявные `using`, версия языка) заданы в `Directory.Build.props`, чтобы контейнерная сборка не расходилась с локальной. Образы backend собираются общим Dockerfile с параметром `.csproj`; SPA идёт отдельным образом с Nginx. Ниже разобраны не каталоги сами по себе, а те фрагменты, без которых нельзя воспроизвести импорт, сопоставление, выбор оффера, доставку события в индекс и смену стадии счёта. Полные тексты генератора КП, перехватчика аудита, консьюмера NATS и миграции схемы вынесены в приложения А–В.

## 5.1 Организация программного решения

Зависимости направлены к домену: проект `ProcurementSystem.Domain` не ссылается ни на инфраструктуру, ни на веб-хост, и в нём живут сущности, перечисления статусов и контракты внешних зависимостей (`ISearchEngine`, `IEventBus`, шлюзы учёта и склада) [10, 11]. Интерфейсы внешних систем намеренно объявлены там же, чтобы прикладная логика могла быть написана до выбора конкретного брокера или поискового движка. Контроллеры принимают DTO, проверяют политику авторизации и вызывают прикладной сервис; сами сервисы пользуются контекстом EF Core и доменными методами, а не дублируют правила перехода в HTTP-слое. Такое разделение позволяет менять адаптер брокера или поискового движка, не трогая жизненный цикл счёта.

Вынесенные сервисы на `ProcurementSystem.Infrastructure` не ссылаются: у каждого свой `DbContext` и копия прикладной логики, потому что жёсткая ссылка на инфраструктуру монолита закрепила бы связность, которую поэтапный вынос как раз разрывает [14]. Следствие видно прямо в дереве исходников: импортёр Excel, генератор КП, матчер и процессор Outbox существуют и в монолите, и в соответствующем сервисе, поэтому поведение приходится сверять синхронно, пока миграция не закончена. Общий class library прикладных сервисов отложен: он уменьшил бы дублирование, но снова собрал бы вынесенные процессы вокруг одного пакета монолита. Шлюз YARP не зависит ни от `Domain`, ни от `Infrastructure` и только маршрутизирует HTTP [18], а раскладка каталогов, из которой следует этот принцип, приведена в таблице 27.

## 5.2 Импорт прайс-листов

Импорт вызывается `POST /api/pricelist/import?vendorId=...` (multipart) и для `.xlsx` читается ClosedXML [26]. Бинарный `.xls` распознаётся по OLE2-сигнатуре (`D0 CF 11 E0`), читается NPOI [27], все листы переносятся в промежуточную книгу ClosedXML; дальше оба формата идут одним конвейером маппинга. Две библиотеки нужны потому, что ClosedXML не читает составной OLE2-документ, а держать два полных конвейера маппинга дороже, чем один промежуточный перенос. Если бы `.xls` отвергался, часть поставщиков осталась бы за контуром, поскольку их выгрузки до сих пор приходят в старом формате Excel.

Положение заголовка в файле не фиксировано, потому что реальные прайсы открываются шапкой с логотипом и контактами, а таблица начинается на десятой строке или на втором листе. Импортёр перебирает листы и первые 30 строк, пока не найдёт одновременно артикул, наименование (или «номенклатуру») и цену. Если поставщик приводит обе цены, за основу берётся колонка «без НДС»: налог начисляет генератор коммерческого предложения, и хранение уже включённого налога привело бы к двойному учёту при расчёте итогов, что видно в листинге 1. Производитель, срок и остаток опциональны: при пустом сроке берётся значение поставщика по умолчанию, при пустом остатке подставляется ноль. Иерархия со вспомогательных листов (колонки «N уровень иерархии») собирается в путь с разделителем ` / `.

Листинг 1 — Поиск заголовка и выбор колонки цены без НДС

```csharp
    private static ColumnMap? DetectColumns(IXLWorksheet ws)
    {
        foreach (var row in ws.RowsUsed().Take(30))
        {
            // …
            var sku = Find(headers, h => h.StartsWith("артикул"));
            if (sku is null) continue;

            var name = Find(headers, h => h.Contains("наименование") || h.Contains("номенклатура"));
            // Приоритет цене «без НДС»: Price в системе хранится без НДС (НДС добавляет генератор КП).
            var price = Find(headers, h => h.Contains("цена") && h.Contains("без ндс"))
                     ?? Find(headers, h => h == "цена")
                     ?? Find(headers, h => h.Contains("базовая цена"))
                     ?? Find(headers, h => h.Contains("цена"));
            if (name is null || price is null) continue;   // «Артикул» есть, но это не строка заголовков

            return new ColumnMap(row.RowNumber(), sku.Value, name.Value,
                Find(headers, h => h.Contains("производитель")),
                Find(headers, h => h.Contains("категория")),
                price.Value,
                Find(headers, h => h.Contains("срок")),
                Find(headers, h => h.Contains("остаток")));
        }
        return null;
    }
```

Пустая строка без артикула пропускается как групповой разделитель и не попадает в список ошибок, иначе шапка разделов EKF давала бы тысячи ложных отказов; нечисловая цена фиксируется по номеру строки и товар не создаёт. Пустое наименование не считается ошибкой: вместо него подставляется сам артикул, потому что часть прайсов держит код в отдельной колонке, а имя заполняет не всегда. Повтор артикула внутри файла даёт предупреждение с номерами строк, но загрузку не блокирует: применяется последняя цена, чтобы оператор видел конфликт, а не терял весь файл. Некорректный файл не даёт необработанный HTTP 500: перехват исключения пишет «Структура файла не распознана», архив всё равно сохраняет оригинал.

Для корректной строки выполняется upsert товара и оффера пакетами по 500 записей, потому что построчный `SaveChanges` на прайсе в десятки тысяч строк растягивал бы импорт на минуты, а изменение цены создаёт `PriceHistoryEntry` в той же транзакции. После изменения каталога в тот же `DbContext` кладётся `OutboxMessage` с событием `ProductUpserted`, и только затем вызывается сохранение; запись в Outbox и последующая публикация пакета показаны в листинге 2. Транзакционный Outbox выбран вместо прямой публикации в брокер из импортёра: если NATS недоступен в момент записи товара, событие останется в PostgreSQL и уйдёт позже, а индекс не «потеряет» строку [12, 13]. Фоновый `OutboxProcessor` раз в секунду читает неотправленные сообщения (до 200 штук), публикует их в JetStream по subject `procurement.{TypeName}` и проставляет `ProcessedAtUtc`. Если публикация прошла, а `SaveChanges` процессора не прошёл, сообщение уйдёт повторно: это доставка at-least-once, которую потребитель обязан переживать идемпотентным upsert [13, 21].

Листинг 2 — Запись Outbox в одном контексте с данными и публикация в NATS

```csharp
    public static void EnqueueEvent<T>(this AppDbContext db, T evt) where T : class
    {

        });
    }
    // …
        var batch = await db.OutboxMessages
            .Where(m => m.ProcessedAtUtc == null)
            .OrderBy(m => m.OccurredAtUtc)
            .Take(200)
            .ToListAsync(ct);

        {

```

Каждая загрузка архивируется целиком: имя файла, двоичное содержимое, поставщик, пользователь и счётчики, чтобы спорную цену можно было разобрать по оригиналу, а не по уже изменённому офферу. Контрольный прогон реального прайса EKF дал 20 884 строки за около 33 с, создал 20 780 товаров и отклонил 92 строки «Цена по запросу» с диагностикой; эти числа характеризуют конкретный файл и стенд, а не промышленную производительность. Повторная загрузка того же файла не ломает архив: каждая попытка получает свою запись, даже если часть строк уже есть в каталоге. ## 5.3 Каталог, поиск и сопоставление

Каталог даёт CRUD товаров, поставщиков и производителей, офферы, историю цен и фильтр по иерархии, потому что без этих сущностей генератор КП не из чего выбирать. Витрина `/ecatalog` добавляет карточку, аналоги, сравнение и подборку, которая может стать спецификацией. Источник истины по номенклатуре остаётся PostgreSQL [19]: индекс Meilisearch только повторяет то, что уже записано, и его недоступность не должна блокировать импорт [22]. Worker подтверждает обработку `Ack` и возвращает сообщение в очередь `Nak` при ошибке индексации; полный цикл потребителя приведён в приложении Б.

При импорте спецификации сначала ищется точный SKU, а для остальных строк живой путь через шлюз (`ProcurementSystem.Services.Matching`, маршрут YARP с `Order: 5`) собирает кандидатов TF-IDF posting-листом, префиксом артикула и соседями категории лучшего хита. Копия матчера в монолите дополнительно запрашивает Meilisearch (top-12) и молча переживает отказ индекса, чтобы поиск по каталогу оставался вспомогательным, а не обязательным. Перед записью `ProductId` проверяется наличие товара в каталоге, иначе экран мог бы подставить идентификатор, которого уже нет в PostgreSQL. Экран сопоставления показывает вид совпадения, вероятность, косинус и текстовую причину; пользователь применяет гипотезы выше порога или выбирает товар вручную.

Порядок шагов в листинге 3 выбран сознательно: точный артикул получает `P ≈ 0,99` без модели, потому что совпадение SKU в закупках считается достаточным основанием, а логрегрессия на шести признаках не должна «перебить» его меньшим числом. Кандидаты без точного SKU собирает `CollectCandidates`: posting-лист TF-IDF, префикс артикула длиной от трёх символов и до двадцати соседей категории лучшего хита. Неточные кандидаты ранжируются по виду совпадения и вероятности, в выдачу попадает не больше `take` гипотез (от 1 до 15). Ограничение нужно экрану, а не модели: оператору достаточно короткого списка, который он может подтвердить или отвергнуть.

Листинг 3 — Сопоставление строки: точный артикул, затем кандидаты TF-IDF

```csharp
    public async Task<IReadOnlyList<MatchSuggestion>> SuggestAsync(
        string? sku, string name, int take = 5, CancellationToken ct = default)
    {
        // …
        var hits = new Dictionary<Guid, MatchSuggestion>();

        if (!string.IsNullOrWhiteSpace(sku) && cache.Sku.TryGetValue(sku.Trim(), out var exactId)
            && cache.Rows.TryGetValue(exactId, out var exact))
        {
            hits[exactId] = ToSuggestion(exact, sku, name, MatchKind.ExactSku, forceP: 0.99);
        }

        if (!string.IsNullOrWhiteSpace(name))
        {
            foreach (var id in CollectCandidates(sku, name))
            {
                if (hits.ContainsKey(id) || !cache.Rows.TryGetValue(id, out var row)) continue;
                hits[id] = ToSuggestion(row, sku, name, KindOf(sku, name, row));
            }
        }

        return hits.Values
            .OrderByDescending(h => h.Kind == MatchKind.ExactSku)
            .ThenByDescending(h => h.Probability)
            .Take(take)
            .ToList();
    }
```

Модель сопоставления использует вектор из шести признаков на отрезке `[0; 1]`, которые считаются по строке заявки и по карточке товара. Смысл каждого признака сведён в таблицу 29: без этой раскладки веса логрегрессии нельзя интерпретировать на защите. TF-IDF строится по словесным токенам и символьным 3-граммам сжатой строки, чтобы опечатка вроде перестановки букв не обнуляла косинус. Признак категории обнуляется, если косинус имени ниже 0,12 и Jaccard ниже 0,15, иначе сосед по разделу каталога получал бы ложную поддержку при совершенно другом наименовании.

Таблица 29 — Признаки модели сопоставления

| № | Признак | Смысл |
|---|---|---|
| 1 | `skuExact` | полное совпадение артикула |
| 2 | `skuFuzzy` | нормированное расстояние Левенштейна |

Вероятность совпадения задаётся логистической моделью `P(y = 1 | x) = σ(b + wᵀx)`, где `σ(z) = 1 / (1 + e^(−z))`, а вектор `x` как раз те шесть признаков таблицы 29. Как видно из листинга 4, начальные веса `[3,2; 1,8; 2,6; 1,4; 0,9; 0,5]`, `b = −2,2`: точный артикул и косинус имени весят больше категории, что совпадает с приоритетом ТЗ. Насыщение сигмоиды при `|z| > 20` отсекает переполнение `exp` и не меняет решение оператора. Нейронные эмбеддинги и внешний сервис ранжирования отвергнуты, потому что на объёме каталога курсовой TF-IDF и линейная модель считаются в процессе API без GPU.

Листинг 4 — Логистическая регрессия: prior и вероятность совпадения

```csharp
    public LogisticRegression()
    {
        Weights = [3.2, 1.8, 2.6, 1.4, 0.9, 0.5];
        Bias = -2.2;
    }

    public double Predict(double[] x)
    {
        var z = Bias;
        for (var i = 0; i < Dim; i++) z += Weights[i] * x[i];
        if (z > 20) return 1;
        if (z < -20) return 0;
        return 1.0 / (1.0 + Math.Exp(-z));
    }
```

Модель дообучается 25 эпох SGD с L2-регуляризацией 0,002 и затухающим шагом `lr / (1 + 0,04 · epoch)`. Пары строятся синтетически по каталогу (стратифицированная выборка до 2000 позиций): товар с самим собой и с опечаткой в имени дают положительные примеры, случайный другой товар даёт отрицательный, поэтому решение нельзя представлять как обученное на фактических кликах закупщиков. Генераторы `Random(42)` для выборки и `Random(7)` для перемешивания эпох фиксируют порядок, чтобы повторный прогрев кэша на том же каталоге давал те же веса. Кэш `MatchingModelCache` живёт в процессе и пересобирается, когда меняется число позиций каталога.

Порог импорта спецификации равен `P ≥ 0,5`, а для подстановки в КП допускается `P ≥ 0,40` без изменения самой спецификации, чтобы генератор мог опереться на аналог там, где оператор ещё не подтвердил гипотезу. После выбора товара стратегия актуальности считает линейный score офферов, разбор которого дан в п. 5.4. Пороги разведены намеренно: запись в заявку требует большей уверенности, чем пробный расчёт стоимости. Экран `/specifications/:id/match` показывает обе величины, чтобы РП видел, почему строка подставилась в КП, но не закрепилась в спецификации.

## 5.4 Генератор коммерческого предложения

`QuoteGenerator.GenerateAsync` загружает спецификацию, сопоставления, товары, overrides, офферы, историю цен и скидки пакетно, затем линейно строит строки. Схема N+1 исключена, потому что на спецификации из сотен позиций она превращала бы сравнение четырёх стратегий в серию запросов к каждой строке. Кандидат содержит поставщика, исходную и эффективную цену, срок, остаток, скидку и момент последней цены, а фильтр наличия оставляет только офферы, покрывающие количество строки. Override проверяется до стратегии: ручной выбор РП не должен быть переписан минимумом цены.

Скидки поставщика и производителя не суммируются: если задана скидка вендора, она имеет приоритет, иначе берётся скидка производителя товара. Эффективная цена `p_eff = round(p × (1 − d / 100), 2)` считается один раз на кандидата и дальше используется всеми стратегиями, чтобы сравнение шло по сумме к оплате, а не по «витринной» цене без скидки. В листинге 5 этот расчёт стоит рядом с правилом выбора: `MinCost` минимизирует эффективную цену и при равенстве берёт меньший срок; `MinLeadTime` делает наоборот; баланс нормирует цену и срок среди офферов этой позиции в `[0; 1]` и минимизирует взвешенную сумму. Нормировка внутри позиции, а не по всему каталогу, нужна потому, что абсолютные рубли и дни разных номенклатур несравнимы.

Листинг 5 — Эффективная цена со скидкой и выбор оффера по стратегии

    private static double BalancedScore(Candidate c, IReadOnlyList<Candidate> cands, double wPrice, double wLead)
    {
        var sum = wPrice + wLead;
        if (sum <= 0) { wPrice = wLead = 0.5; sum = 1; }
        wPrice /= sum; wLead /= sum;

        decimal minP = cands.Min(x => x.EffectivePrice), maxP = cands.Max(x => x.EffectivePrice);
        int minL = cands.Min(x => x.LeadTimeDays), maxL = cands.Max(x => x.LeadTimeDays);
        double pSpan = (double)(maxP - minP), lSpan = maxL - minL;
        double nP = pSpan > 0 ? (double)(c.EffectivePrice - minP) / pSpan : 0;
        double nL = lSpan > 0 ? (c.LeadTimeDays - minL) / lSpan : 0;
        return wPrice * nP + wLead * nL;
    }

## 5.5 Согласование, счёт, заказ и приёмка

Согласование создаётся из спецификации и выбранной стратегии КП, чтобы коммерческий блок видел ту же себестоимость, что и руководитель проекта на экране сравнения. Операция наценки считает продажную цену и маржу доменными методами `Approval.CalcSellPrice` и `CalcMarginPercent`: цена клиенту равна себестоимости, умноженной на `(1 + наценка / 100)`, маржа равна `(цена − себестоимость) / цена × 100`. Формулы живут в сущности, а не в контроллере, чтобы HTTP-слой не стал вторым местом, где можно ошибиться знаком [11]. Решение по политике `approve` при `approved: true` сразу создаёт счёт с автором «Система (авто)». Согласование и счёт пишутся двумя сохранениями: сначала фиксируется решение, затем вызывается создание счёта. Повторный POST счёта идемпотентен по `ApprovalId` и возвращает уже существующий документ, а `resubmit` доступен только для отклонённого согласования, причём комментарий предыдущего отказа не стирается.

Номер счёта имеет вид `NOC-год-NNN` и выдаётся последовательно по префиксу текущего года, а строки счёта являются снимком согласованного варианта КП, потому что смена прайса не должна переписывать уже выставленную сумму. Вложения подчинены политике бухгалтерии и ограничены по размеру, чтобы журнал документов не превратился в файловое хранилище произвольных вложений. Переход статуса разрешён только на следующий шаг линейной цепочки; «Отменён» допустим из любого не финального состояния. Правило роли и правило линейности разведены специально, что видно в листинге 7. `ActorMaySet` отвечает на вопрос «кто имеет право поставить эту стадию»: «Согласован» ставит коммерческий блок (`CanApprove`), последующие включая отмену выставляет бухгалтерия (`CanPostPayment`), системный актор склада не ограничивается. `CanTransitionTo` отвечает на другой вопрос, допустим ли шаг из текущего состояния, а отказ по роли даёт HTTP 403 и недопустимый переход даёт 409, чтобы клиент не путал «нет права» и «нельзя перепрыгнуть стадию».

Заказ создаётся из стратегии КП, копирует строки и в той же операции уменьшает `StockQuantity`, потому что ТЗ связывает выбор варианта с резервом, а не с отдельным шагом «подтвердил поставщик». Отмена идемпотентна: если статус уже `Cancelled`, резерв не возвращается второй раз, потому что повтор текущей стадии выходит до корректировки склада. Резерв на стадии `Draft` упрощает учебный стенд: промышленный контур мог бы держать мягкую бронь до `Placed`, но тогда отмена черновика требовала бы отдельного события склада.

Приёмка копирует строки заказа, после чего пользователь вводит факт, а проведение вызывает `IWarehouseGateway` и `IAccountingGateway`. Идентификатор спецификации читается до вызова шлюзов, чтобы падение HTTP не оставило внешние системы с проведённой приёмкой без события. Стендовые адаптеры не обмениваются с реальными 1С/WMS и пишут собственные спаны `integration.wms.receipt` и `integration.1c.post`. Вынесенный Logistics публикует `GoodsReceiptCompleted`; Commercial идемпотентно доводит счёт до «ПришёлНаСклад» и «ОтраженоВ1С».

## 5.6 Безопасность и наблюдаемость

Политики авторизации заданы явно в каждом хосте, который принимает JWT, потому что вынесенный сервис не должен полагаться на то, что шлюз уже проверил роль. Скрытие пунктов меню в SPA не заменяет серверную проверку: клиент может спрятать кнопку, сервер всё равно отвергнет чужую роль. Соответствие политик ролям и типичным операциям сведено в таблицу 30, чтобы было видно, какие операции закрыты одной политикой, а какие требуют дополнительного правила в домене. Политика `setInvoiceStatus` выдана и коммерческому блоку, и бухгалтерии, а тонкое разграничение стадий оставлено домену (листинг 7), чтобы не плодить отдельную политику на каждую ступень цепочки.

`AuditMiddleware` фиксирует аутентифицированные POST, PUT, DELETE и PATCH после обработки запроса и глотает собственные сбои, чтобы журнал не ломал основную операцию. Перехватчик EF `AuditSaveChangesInterceptor` дополнительно пишет «было → стало» для Discount, Order, Invoice, Approval, GoodsReceipt и PriceListItem. В листинге 8 видно, почему массовый импорт не зашумляет журнал: новые офферы (`Added` + `PriceListItem`) пропускаются, их цену фиксирует история цен, а в аудит попадают только изменения существующих офферов. ## 5.7 Интерфейс, уведомления и развёртывание

Клиентское приложение собрано на React 19 и TypeScript, потому что рабочий кабинет должен оставаться типизированным SPA, а не набором серверных страниц [24]. Сборку даёт Vite, маршрутизацию React Router, кэш запросов TanStack Query, вход `react-oidc-context`; типизированный клиент передаёт access token в заголовке к шлюзу. Уведомления идут через колокольчик с опросом счётчика каждые 30 с (`refetchInterval: 30_000`) и через SMTP, а на стенде письма принимает MailHog, потому что корпоративный SMTP в учебном контуре недоступен. Корпоративный мессенджер не подключён и в ТЗ не требовался как обязательный канал.

Контейнеры стенда и порты хоста сведены в таблицу 31, чтобы по одному взгляду было ясно, какой процесс слушает снаружи Compose. Matching вынесен на 5174, Retail на 5176: оба получают трафик в Docker через шлюз, хотя в ранней раскладке раздела их не выделяли отдельной строкой. Секреты стенда заданы значениями по умолчанию для локального запуска, потому что учебный контур не ходит во внешние облака. Compose не обеспечивает высокую доступность [25]: отказ узла или потеря тома на учебном стенде автоматически не отрабатывается.

## 5.8 Соответствие техническому заданию

Статус «готово» означает backend и живой экран с основным поведением, совпадающим с формулировкой ТЗ с учётом осознанных упрощений модели. «Частично» значит, что основной сценарий есть, но нет отдельных шагов, полей или каналов, которые ТЗ описывает рядом с ядром. «Мок» означает контракт без внешней системы: шлюз вызывается, обмен с 1С или WMS на стенде не идёт.
