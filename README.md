# Кварц

Система считает коммерческое предложение из заявки и прайсов поставщиков,
проводит его через наценку и счёт и фиксирует заказ так, чтобы поздняя правка
каталога уже не меняла цены.

Курсовой проект, ЧелГУ. Решение: `ProcurementSystem.slnx`.

.NET 10 · ASP.NET Core · EF Core, PostgreSQL 17 · YARP · Keycloak (OIDC/JWT) ·
NATS JetStream · Meilisearch · React 19, TypeScript, Vite · ClosedXML, NPOI, QuestPDF ·
xUnit

## Как идёт документ

Один контур, несколько акторов. Каждый шаг — отдельный агрегат, не «ещё одна
стадия той же таблицы».

```
прайс Excel → каталог (офферы, история цены)
     ↓
заявка (спецификация)
     ↓ точный артикул / TF-IDF + логрегрессия
сопоставленные позиции
     ↓ QuoteGenerator, один проход
четыре листа КП: цена / срок / баланс / актуальность
     ↓ себестоимость выбранного листа
согласование: наценка РП → решение КБ
     ↓ при «Согласовано»
счёт NOC (снимок строк) → оплата бухгалтерией
     ↓
заказ (снимок цен и поставщиков, резерв остатка)
     ↓
приёмка склада → событие → счёт «пришёл / отражено в 1С»
```

РП собирает заявку и выбирает лист КП, сам себе согласовать не может.
Коммерческий блок ставит «Согласован» на счёте. Дальше — только бухгалтерия.
Склад двигает счёт системным актором, без HTTP от бухгалтера.

## Как устроены сервисы

Стенд в состоянии **strangler fig**. SPA ходит в Gateway на YARP. Шлюз режет
URL по префиксу и отдаёт вынесенному процессу; что ещё не вынесли — модульному
монолиту.

```
React SPA ──OIDC──> Keycloak
     │
     └── /api (JWT) ──> Gateway (YARP)
                          ├── Auth
                          ├── Catalog     номенклатура, прайсы, остаток
                          ├── Quoting     спецификации, генератор КП
                          ├── Matching    TF-IDF + логрегрессия
                          ├── Commercial  согласование, счета
                          ├── Ordering    заказы-снимки
                          ├── Logistics   приёмка, шлюзы 1С/WMS
                          ├── Notifications
                          ├── Retail
                          └── Api         поиск, проекты, аудит

Catalog ──(Outbox)──> NATS JetStream ──> Worker ──> Meilisearch
Logistics ──(Outbox)──> GoodsReceiptCompleted ──> Commercial
```

У каждого вынесенного сервиса своя схема PostgreSQL. Чужой агрегат — голый
`Guid` без FK: Quoting не джойнит таблицу товаров Catalog, берёт офферы снимком
по HTTP. Matching своей схемы не держит.

Шлюз JWT не проверяет — проксирует `Authorization`. Валидация — в каждом
сервисе. Так префикс можно переключить, не участвуя в авторизации.

За сменой реализации, не домена:

- `ISearchEngine` — сейчас Meilisearch;
- `IEventBus` — сейчас NATS JetStream;
- `IAccountingGateway` / `IWarehouseGateway` — сейчас моки под 1С и WMS.

NATS + свой Outbox вместо RabbitMQ + MassTransit: у MassTransit нет транспорта
под NATS. Meilisearch вместо Elasticsearch — один узел за тем же интерфейсом.

## Как считается КП

Генератор не ходит в базу на каждую позицию. Один проход: спецификация,
все офферы по её товарам, активные скидки, ручные override.

Эффективная цена = цена × (1 − скидка/100). Скидка поставщика важнее скидки
производителя. Override бьёт стратегию: «выбрано вручную».

| Лист | Правило |
|------|---------|
| Мин. цена | дешевле со скидкой, при равенстве — быстрее |
| Мин. срок | быстрее, при равенстве — дешевле |
| Баланс | цена и срок нормируются среди кандидатов на **эту** позицию |
| Актуальность | score: сходство × свежесть прайса × остаток × цена × срок |

Каждая строка несёт `SelectionReason` — почему взят этот поставщик, а не сосед.
НДС считается отдельно: в листе всегда суммы без и с налогом. Позиция без
оффера в итог не входит.

Согласование не считает себестоимость заново своими формулами: берёт выбранный
лист у того же генератора. Счёт при создании вызывает его ещё раз с той же
стратегией, скидками и override — и кладёт построчный снимок в `InvoiceLine`.
Поздний пересчёт каталога этот снимок не трогает.

Экспорт листа — Excel (ClosedXML) и PDF (QuestPDF).

## Как строка заявки становится товаром

ТЗ оставляло алгоритм нечёткого поиска на выбор. Конвейер:

1. точный артикул → `P ≈ 0.99`;
2. кандидаты: TF-IDF (токены + символьные 3-граммы) и top-12 Meilisearch,
   плюс соседи по категории;
3. шесть признаков в `[0, 1]`: артикул, нечёткий артикул, косинус имени,
   Jaccard, категория, производитель;
4. логистическая регрессия. Импорт пишет `ProductId` при `P ≥ 0.5`.
   Генератор подставляет аналог в расчёт КП при `P ≥ 0.40`, спецификацию
   при этом не меняет.

Модель учится на каталоге без ручной разметки: плюс — товар и он же
с перестановкой букв, минус — случайный другой. Дешёвый оффер с прайсом
двухлетней давности и нулевым остатком проигрывает чуть более дорогому,
но свежему и в наличии: полураспад актуальности прайса — 45 дней.

Импорт прайса ищет строку заголовков на любом листе книги, `.xlsx` и старый
`.xls`, дубли SKU не роняют загрузку. Изменение цены пишет историю в той же
транзакции, что и оффер.

## Как заказ переживает смену прайса

Заказ — не ссылка на живые офферы. Это снимок выбранного листа: цена,
поставщик, количество. Каталог после `Placed` может поехать — строки заказа нет.

В тот же момент резервируется остаток в Catalog. Отмена возвращает резерв,
ниже нуля не уходим. Переходы статуса живут в сущности (`CanTransitionTo`),
не в контроллере: соседний сервис не поставит `Completed` из `Draft`.

Счёт — линейная цепочка из восьми стадий, шаг только на следующую
(`ti == ci + 1`). Ранняя версия разрешала перескок — это регрессия, закрытая
в домене. «Отменён» допустим из любого нефинального состояния.

Приёмка снимает заказ ещё раз и считает расхождение «принято − заказано».
Проведение публикует `GoodsReceiptCompleted`. Commercial слушает JetStream
и идемпотентно двигает счёт «ожидание поставки → пришёл → отражено в 1С».
Бухгалтер для этого шага не нужен.

## Как индекс не расходится с каталогом

Писать в PostgreSQL и в Meilisearch двумя вызовами нельзя: между ними процесс
может умереть, и поиск будет врать.

`ProductUpserted` кладётся в Outbox тем же `SaveChanges`, что и строка товара.
Нет коммита — нет события. Фоновый процессор публикует в JetStream, Worker
индексирует. Брокер лёг — процессор повторит цикл. Индексация идемпотентна,
повтор после `Nak` безопасен.

## Как роли режут контур

Не «admin / user». Шесть ролей совпадают с акторами процесса: администратор,
руководитель проекта, коммерческий блок, бухгалтерия, склад, наблюдатель.

Политики на эндпоинтах повторяют домен: РП задаёт наценку, КБ принимает
решение, «Согласован» на счёте ставит только КБ, оплату и дальше — бухгалтерия,
приёмку — склад. Чужой шаг — 403, недопустимый переход статуса — 409.

Журнал аудита пишет «было → стало» по белому списку сущностей. Правила
жизненного цикла из другого сервиса не обойти: они в `Approval`, `Invoice`,
`Order`, `GoodsReceipt`, не в обвязке HTTP.
